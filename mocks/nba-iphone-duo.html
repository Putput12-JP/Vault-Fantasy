How the page knows which layout to use

Picked by what the screen can do, not by guessing the phone model. Each row is a CSS check; nothing sniffs the browser name.

Touch fixes kept from #314 (and checked against the mobile-native guide)

  • No grey tap flash, no 300ms tap delay, fields at 16px so iOS doesn't zoom, zoom itself never disabled.
  • No pull-to-refresh hijack on the page; inner lists use overscroll-behavior:contain.
  • Separate status-bar colours for dark and light.
  • Add: hover effects only on screens with a real pointer, so a tapped row doesn't stay lit.
  • Add: app height from 100dvh, never 100vh, so the page fits when Safari's bar shows and hides.
  • Add: safe-area padding on all four sides, since the outer screen puts the Dynamic Island on the side.

What changes from today

  • Today's fold layouts use width cut-offs (561-820px and 821-1100px). The open book (890 wide) gets the left icon sidebar and a 4-across tile row that doesn't line up with the fold.
  • The closed Duo (466 wide) gets the normal phone layout, so the bottom bar eats height on a screen that is already short.
  • New: right-edge strip on short screens, two-page list + detail when open, even columns everywhere, fold poses as an add-on.
  • Layout only. No model, number or tracking change.

Needs a real iPhone Duo before shipping

  • Point sizes come from Apple's pixel counts divided by 3; Apple doesn't publish them. Confirm with innerWidth on the device.
  • Where the Dynamic Island sits on each screen in Safari and in a home-screen app.
  • The fold APIs are off by default in Safari 27.1 and may change, so the main layout can't depend on them.
  • Which side of Split View the page is on (frame 5).
